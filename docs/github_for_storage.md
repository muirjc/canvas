Nothing in the concepts changes, because the branching, PR, and CODEOWNERS parts are language-agnostic. Only the tooling layer moves, and TypeScript gives you one real advantage: the compiler can enforce part of the architecture model.

## Tooling translation

| Concern | Python | TypeScript |
|---|---|---|
| Frontmatter/model schemas | Pydantic | **Zod** (or Valibot, TypeBox) |
| Test runner | pytest | **Vitest** |
| Lint/format | ruff | **ESLint + Prettier**, or **Biome** |
| Type checking | mypy | **`tsc --strict`** |
| Pre-commit hooks | pre-commit | **Husky + lint-staged**, or **Lefthook** |
| Layer/boundary rules | import-linter | **dependency-cruiser**, **eslint-plugin-boundaries**, or **ArchUnitTS** |
| Dependency pinning | uv.lock | `pnpm-lock.yaml` / `package-lock.json` |
| API breaking-change diff | OpenAPI diff | **oasdiff** (language-independent) |
| Docs site | MkDocs | **VitePress**, **Docusaurus**, or **Astro Starlight** |
| Markdown parsing | python-frontmatter | **gray-matter**, **unified/remark** |
| Diagram render check | mermaid-cli | **@mermaid-js/mermaid-cli** (`mmdc`), or D2/Structurizr CLI |

For a monorepo with several packages (model, validators, docs site), use **pnpm workspaces** with **Turborepo** or **Nx** so CI only rebuilds what changed.

## The TypeScript advantage: types as the compiler

Earlier I said architecture has no compiler, so CI has to stand in for one. In TypeScript you can make the model itself typed, so many integrity errors become compile errors:

```ts
// model/components.ts
export const components = {
  "claims-api":   { kind: "service", owner: "claims-team" },
  "pricing-svc":  { kind: "service", owner: "pricing-team" },
  "policy-db":    { kind: "datastore", owner: "data-team" },
} as const satisfies Record<string, ComponentDef>;

export type ComponentId = keyof typeof components;

// A relationship can only reference components that exist.
export const relationships: Relationship<ComponentId>[] = [
  { from: "claims-api", to: "policy-db", protocol: "SQL" },
  // { from: "claims-api", to: "billing-svc" }  // compile error: unknown ID
];
```

A typo or a reference to a removed component fails `tsc` immediately. Renaming a component with your editor's rename-symbol updates every reference. Diagrams are then generated by a small TS script that emits Mermaid or D2 from the model, which gives you the single-source-of-truth model and derived views I described before.

## Document-level validation with Zod

Markdown artifacts (ADRs, specs) still need runtime validation, since frontmatter isn't visible to the compiler:

```ts
import { z } from "zod";

export const AdrFrontmatter = z.object({
  id: z.string().regex(/^ADR-[a-z0-9-]+$/),
  title: z.string().min(1),
  status: z.enum(["proposed", "accepted", "superseded", "deprecated"]),
  supersedes: z.array(z.string()).default([]),
  owners: z.array(z.string()).min(1),
  relatesTo: z.array(z.string()).default([]),   // REQ-*, DES-*, component IDs
});
export type Adr = z.infer<typeof AdrFrontmatter>;
```

You can generate JSON Schema from the same Zod definitions (`zod-to-json-schema`) so editors give authors inline validation and autocomplete in frontmatter.

## Graph-integrity checks in Vitest

```ts
import { describe, it, expect } from "vitest";
import { loadAllArtifacts } from "../src/loader";

describe("architecture graph", () => {
  const artifacts = loadAllArtifacts();              // gray-matter + Zod parse
  const ids = new Set(artifacts.map(a => a.id));

  it("has unique IDs", () => {
    expect(ids.size).toBe(artifacts.length);
  });

  it("has no dangling references", () => {
    const dangling = artifacts.flatMap(a =>
      [...a.supersedes, ...a.relatesTo]
        .filter(ref => !ids.has(ref) && !(ref in components))
        .map(ref => `${a.id} -> ${ref}`));
    expect(dangling).toEqual([]);
  });

  it("has no supersession cycles and one accepted ADR per lineage", () => {
    /* walk the supersedes chain */
  });
});
```

The CI check list from before stays the same: schema validation, ID uniqueness, link integrity, status-transition rules (diff against `main` to catch an `accepted` ADR going back to `proposed`), render checks, and requirement-to-design-to-test coverage.

## Conformance of code to design

If the implementation is also TypeScript, fitness functions get easier. `dependency-cruiser` or `ArchUnitTS` can assert in CI that dependencies match the declared model: for example, that `claims-api` never imports directly from `policy-db` internals, or that a relationship absent from the model can't appear in code. Because the model is typed TS, those tools can read it directly instead of parsing a separate format.

